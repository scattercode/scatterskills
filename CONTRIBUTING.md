# Contributing

Contributions welcome — a fix to an existing skill, or a new one.

## What makes a good skill

A skill captures a *method*, not a lookup table. The test is whether someone
following it would produce good work on a problem you did not anticipate.

- **Explain why, not just what.** Instructions that say what to do produce
  literal compliance. Instructions that explain why a step matters let the
  reader adapt when the situation differs from the one you had in mind. If you
  find yourself writing MUST in capitals, that is usually a sign the reasoning
  is missing.
- **Generalise past your example.** Skills are usually written straight after
  doing the thing once. Reread the draft and ask which parts only make sense
  for that specific case, then lift them.
- **Say what good looks like.** Where a skill produces a document or an
  artefact, describe the qualities that distinguish a good one from a
  mediocre one. That is the part that is hard to work out independently.
- **Keep `SKILL.md` short.** Under about 500 lines. Detail belongs in
  `references/`, which is read only when needed.

## Structure

```text
skill-name/
├── SKILL.md          required — frontmatter plus instructions
├── references/       optional — detail loaded on demand
├── scripts/          optional — executable helpers
└── assets/           optional — templates, images used in output
```

`SKILL.md` needs YAML frontmatter with `name` and `description`:

```yaml
---
name: skill-name
description: What it does, and when to use it. Both matter.
---
```

**The description does the most work in the whole file.** It is the only part
always in context, and it alone determines whether the skill gets used. Write
what the skill does *and* the situations that should trigger it, including
phrasings a user might reach for without naming the skill. Skills tend to be
under-triggered rather than over-triggered, so err towards being explicit
about when it applies.

Directory name and `name` should match, both lower-case with hyphens.

## Style

- British English
- Sentence case for headings
- Second person or imperative in instructions
- Prefer tables to long lists where the content is comparative

## Commits

This repository uses [Conventional Commits](https://www.conventionalcommits.org/),
enforced by a hook shared across all scattercode repositories.

```text
<type>[(scope)][!]: <description>
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`,
`ci`, `chore`, `revert`. Use the skill name as the scope where it applies:

```text
feat(due-diligence-review): add AI governance domain
fix(install): support bash 3.2 on macOS
docs: clarify project-scoped installation
```

Rules the hook enforces: an allowed lower-case type; a non-empty description
with no trailing full stop; a header of 100 characters or fewer, 72 preferred;
a blank line before any body.

Activate the hook in a fresh clone:

```bash
git config core.hooksPath .githooks
```

## Versioning

The version describes the library as a distributable, not any individual
skill.

| Bump | Trigger | Commit |
|---|---|---|
| **Major** | Removing or renaming a skill, or changing a skill's output contract so existing usage breaks | `feat!:` or a `BREAKING CHANGE:` footer |
| **Minor** | Adding a new skill; adding a capability to an existing one | `feat:` |
| **Patch** | Guidance corrections, typos, scaffolding, docs, installer fixes | `fix:`, `docs:`, `chore:`, `refactor:` |

Adding a skill is deliberately *not* a major bump. People install individual
skills, so `./install.sh some-skill` ends up in setup scripts — renaming or
removing one breaks those, while adding one cannot break anything. Treating
every addition as major would also drain the version number of meaning.

A rename is a removal plus an addition. To avoid the major bump, leave a
directory whose `SKILL.md` points at the new name.

## Changelog

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org) from the
commit history, per `cliff.toml`. Do not edit it by hand; if something reads
wrong, fix the commit message or the parser configuration.

## Adding a skill

1. Create the directory with a `SKILL.md`.
2. Add a row to the table in `README.md` — `install.sh` finds skills on the
   filesystem, but people find them in the README.
3. Commit with `feat(skill-name): ...`.

Test the install path before opening a pull request:

```bash
./install.sh --dry-run your-skill-name
./install.sh --list
```

## Testing a skill

There is no automated harness here. The practical approach is to install the
skill, give Claude a realistic task it should cover, and see whether it
triggers and whether the output is what you wanted. Worth trying a task that
*should not* trigger it too — a description that catches everything is as much
of a problem as one that catches nothing.
