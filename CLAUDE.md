# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this project is

**scatterskills** is a shared library of
[Agent Skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview)
for Claude — reusable procedures for work we do often enough that the approach
is worth writing down.

It is a collaborative project. Write documentation and commit messages in the
first person plural, and assume more than one person will read, edit and rely
on anything added here.

The library exists so that a method can be *improved over time*. A skill
written after doing something once is a draft; its value comes from being
revised when it is used again and found wanting. Treat every skill here as
something that will be edited, not as a finished artefact.

There is no application code. This repository is documentation, a shell
installer, and the skills themselves.

## Language

British English throughout — "behaviour", "organise", "licence" (noun),
"analyse". Sentence case for headings, never title case.

## Layout

```text
scatterskills/
├── CLAUDE.md              this file
├── README.md              what skills are, how to install, the catalogue
├── CONTRIBUTING.md        structure, style, commit conventions
├── CHANGELOG.md           generated by git-cliff — never edit by hand
├── LICENSE                MIT
├── cliff.toml             changelog generation config
├── install.sh             installs skills into a Claude skills directory
├── .githooks/commit-msg   Conventional Commits enforcement (shared)
├── .github/workflows/     ci.yml (validation) and release.yml (tag + release)
├── .claude-plugin/        marketplace.json and plugin.json — nothing else
└── skills/
    └── <skill-name>/
        ├── SKILL.md       required — frontmatter plus instructions
        ├── references/    optional — detail loaded on demand
        ├── scripts/       optional — executable helpers
        └── assets/        optional — templates used in output
```

**Skills live under `skills/`, and that path is load-bearing.** The Claude Code
plugin marketplace requires `skills/<name>/SKILL.md` when a plugin source
resolves to the repository root, and `npx skills` scans both the root and
`skills/` — so this one arrangement serves every distribution route. Moving
them back to the root would silently break the marketplace channel.

`install.sh` discovers skills from the filesystem, so adding one needs no edit
to the script — but it does need a row in the README catalogue, and CI fails
if it is missing.

## Distribution

Three routes, all from the same layout:

| Route | Command |
|---|---|
| skills CLI | `npx skills add scattercode/scatterskills` |
| Plugin marketplace | `/plugin marketplace add scattercode/scatterskills` |
| Local script | `./install.sh` |

`.claude-plugin/plugin.json` carries a `version`, and marketplace users only
receive updates when it changes — the release workflow bumps it to match each
tag, so do not edit it by hand.

Validate a skill against the spec before committing:

```bash
skills-ref validate ./skills/<skill-name>
```

## Working on a skill

### Frontmatter

`SKILL.md` requires YAML frontmatter with `name` and `description`:

```yaml
---
name: skill-name
description: What it does, and when to use it.
---
```

The directory name and `name` must match, both lower-case with hyphens. The
spec requires it, and CI enforces it — when they diverge the skill loads under
a name nobody expects, or not at all.

### Naming convention

**Name a skill for the role it plays** — an agent noun ending in `-er` or
`-or`, qualified by domain where the bare noun would be too generic:
`manuscript-copyeditor`, `due-diligence-reviewer`.

This is a deliberate choice, not the documented default, so do not "correct"
it. Anthropic's authoring guidance recommends the **gerund** form
(`processing-pdfs`, `writing-documentation`). But their own library barely
follows it: of the 18 skills in `anthropics/skills`, only two are gerunds,
five are agent nouns (`skill-creator`, `mcp-builder`, `slack-gif-creator`,
`web-artifacts-builder`, `theme-factory`) and the rest are plain domain nouns.
There is no dominant convention to conform to.

Agent nouns won here because they read naturally for skills that act on your
behalf, and because they stay consistent across the library — the gerund form
collapses on the second case, where `due-diligence-reviewing` is unusable.

A generic name is also a practical hazard: the install name becomes the
directory name in `~/.claude/skills/` with no collision suffixing, so a bare
`copyeditor` would clash with anyone else's. Qualify by domain.

**The description does more work than anything else in the file.** It is the
only part always in Claude's context, and it alone determines whether the
skill is used. Write what the skill does *and* the situations that should
trigger it, including phrasings someone might reach for without naming the
skill. Skills tend to be under-triggered rather than over-triggered, so err
towards being explicit about when it applies.

Anthropic's own skills use only `name`, `description` and sometimes `license`
in frontmatter. Do not invent additional keys without a reason — in particular
there is deliberately no per-skill `version` field here; see the versioning
section below.

### Body

Keep `SKILL.md` under about 500 lines. Detail belongs in `references/`, which
is read only when needed — this is what keeps the skill cheap to load.

Write instructions that explain **why**, not only what. Instructions that only
say what to do produce literal compliance; instructions that explain why a
step matters let the reader adapt when the situation differs from the one that
was anticipated. Heavy use of MUST and NEVER in capitals is usually a sign
that the reasoning is missing and should be supplied instead.

Generalise past the example that prompted the skill. Skills are usually
written straight after doing the thing once, and the first draft is always
overfitted to that instance. Reread and lift out anything that only makes
sense for that specific case.

### Testing

There is no automated harness. The practical loop is: install the skill, give
Claude a realistic task it should cover, and see whether it triggers and
whether the output is right. Also try a task that *should not* trigger it — a
description that catches everything is as much of a problem as one that
catches nothing.

Before committing a change to `install.sh`:

```bash
bash -n install.sh                       # syntax
./install.sh --list
./install.sh --dry-run <skill-name>
```

`install.sh` must run on **bash 3.2**, which is what macOS ships. Avoid
`mapfile`, associative arrays, and `${var,,}` — all bash 4+.

## Commits

Conventional Commits, enforced by `.githooks/commit-msg`. Activate the hook in
a fresh clone:

```bash
git config core.hooksPath .githooks
```

Format: `<type>[(scope)][!]: <description>`

Use the skill name as the scope wherever a change is skill-specific:

```text
feat(due-diligence-reviewer): add AI governance domain
fix(install): support bash 3.2 on macOS
docs: clarify project-scoped installation
```

Rules the hook enforces: an allowed lower-case type; a non-empty description
with no trailing full stop; a header of 100 characters or fewer, 72 preferred;
a blank line before any body.

## Versioning

Releases follow [Semantic Versioning](https://semver.org), with the version
describing **the library as a distributable**, not any individual skill.

The mapping is the standard one, and the thing worth being careful about is
that *adding* a skill is not a breaking change:

| Bump | Trigger | Commit |
|---|---|---|
| **Major** | Removing a skill, renaming a skill, or changing a skill's output contract such that existing usage breaks | `feat!:` or `BREAKING CHANGE:` footer |
| **Minor** | Adding a new skill; adding a capability to an existing one | `feat:` |
| **Patch** | Corrections to guidance, typos, scaffolding, documentation, installer fixes | `fix:`, `docs:`, `chore:`, `build:`, `ci:`, `refactor:` |

**Why removal and rename are the breaking cases, and addition is not.** People
install individual skills — `./install.sh due-diligence-reviewer` ends up in
setup scripts and dotfiles. Renaming or removing a skill breaks those; adding
one cannot break anything. Treating every addition as a major bump would also
drain the version number of meaning: a library reaching v12.0.0 because it
contains twelve skills communicates nothing about stability.

A rename is a removal plus an addition. If the old name needs to keep working,
leave a directory containing a `SKILL.md` that points at the new one, and then
it is only a minor.

### Note on the state of the art

Agent Skills are new and there is no established convention to conform to.
Anthropic's own skills repository has no git tags, no changelog, no
contributing guide, and no `version` field in any skill's frontmatter. The
scheme here is therefore a local decision rather than an industry standard —
worth revisiting if a convention emerges, and worth not over-engineering in
the meantime.

If per-skill version tracking becomes genuinely useful — most likely if
someone starts depending on a specific skill's behaviour — add a `version` to
that skill's frontmatter at that point. Do not add it pre-emptively to all of
them.

## Changelog

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org) from the
commit history, per `cliff.toml`. Never edit it by hand. If an entry reads
wrong, fix the commit message or the `commit_parsers` in `cliff.toml`.

Commits generated by tooling should use `chore(release):` or
`chore(changelog):` so the parser skips them.

## Guardrails

- Never edit `CHANGELOG.md` directly.
- Do not add a skill without adding its row to the README catalogue.
- `install.sh` must stay bash 3.2 compatible.
- Every script needs a header comment block explaining its purpose,
  prerequisites, and how to run it.
- Skills must not contain anything that would surprise someone who read only
  the description — no hidden network calls, no data collection, nothing that
  behaves differently from what it says.
